(~1 min) The starting point for this project was Ezequiel. His salary is paid in dollars at one bank, he keeps savings at a second bank, and his debit card is tied to a third account that he tops up as he needs it. Most of what he buys is priced in colones. He tracked all of this in a spreadsheet, which was only accurate for about a week after he updated it. He tried a consumer expense tracker, but it counted the money he moved between his own accounts as spending, it could not keep two currencies apart, and its automatic capture was unreliable. He also invests in an index fund and a small amount of bitcoin, and the number he cares about is what he would actually get back after the broker's deposit, trade, and withdrawal fees. These six needs are the main features of the app.

Solution Overview

The Personal Finances App is a web app that brings in transactions from BAC and Banco Nacional, converts colones to dollars, and shows spending, budgets, and investments in one place.

(~45 s) This is what we built. These are the main parts of the app, and they are not steps in a fixed order. Transactions come in from three places: a Google Apps Script that forwards the bank alert emails from Gmail, the CSV statements that the user downloads from the bank, and manual entry. Each transaction gets one category and any number of tags, and when the user corrects a category, the app can remember it as a rule for that merchant. Amounts in colones are converted to dollars with the official BCCR rate of that day, and the original amount is kept. The app shows where the money went, the progress of each budget, income against spending, and the value of the investments after fees. The design changed a few things from the 1-pagers, for example using USD as the base currency and reading bank emails and statements instead of bank APIs, since no Costa Rican bank offered one for personal accounts.

(~1 min 15 s) This is a simplified version of the attempt 1 architecture diagram, and the link opens the full draw.io version. Everything runs in a personal AWS account in us-east-2, split into three CDK stacks. The web stack serves the Next.js app through CloudFront, with the server running in a Lambda. The API stack has API Gateway with a Cognito JWT authorizer in front of one Lambda, ApiFn, which has all the routes and services. CSV statements are uploaded straight from the browser to a private S3 bucket, and the S3 event starts a second Lambda, ImportWorkerFn, built from the same code. The Gmail script posts each bank email to the ingest route with its own token. The data stack has five DynamoDB tables, and the totals and budgets are updated in the same transaction as each write, so the dashboard reads stored numbers instead of adding everything up. The BCCR token is kept in SSM Parameter Store. We used AWS instead of Vercel or Railway because the backend needs S3 events, a JWT authorizer, and DynamoDB transactions, and the agents could deploy it with one CDK command.

(~1 min) Everything is written in TypeScript: the Next.js app, the API Lambdas, the shared Zod schemas, and the CDK infrastructure. The app is deployed to a personal AWS account. The account only allows us-east-2, and the agents deploy with a role that can only create the services in our architecture, with resource names that start with FinanceApp. The BCCR token is stored in SSM Parameter Store, so it never appears in the code or in the public repo. For each attempt, we change the diagrams on a branch and merge them into main with a pull request. Then we copy the diagrams and the 1-pagers into an agent-a and an agent-b folder on that attempt's branch. Each agent starts in a new session, only reads its own folder, gets the same prompt, and cannot ask questions, so any assumption has to go into its implementation notes. Agent A is Claude Opus 5.5 and agent B is GPT Terra 5.6. Each one deploys its own copy of the app.

(~50 s) In attempt 2, agent A's app computed the right numbers, but each module looked like its own set of tables and forms. For attempt 3, most of the changes are about the screens. We added an app shell and UI kit to the context model as a shared service that every module uses to reach the screen, and the class diagram now specifies every page: the order of its sections, its headline figures, which chart answers which question, its loading, empty, and error states, and its wording. The charts are drawn on the server as SVG, with no chart library, so both agents build the same components instead of each choosing its own. We also added 16 built-in categories and a Settings page for the user's own categories and tags, since the earlier design never said where the list of categories came from. The dashboard now opens on the current month, the portfolio shows how the value splits across holdings and what fees would take on selling, and prices show the time the market traded instead of the time we fetched them. Lastly, we fixed the holding value formula that agent A found. The prompt only changed to give the exact code that removes the SSM parameter that made agent B's web stack fail twice.
